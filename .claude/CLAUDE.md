# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Standards

Follow the coding and commit standards below. They are copies of the user's global style guides, kept in the repo so that cloud sessions have them too.

@context/CODING_STYLE.md

@context/COMMIT_STYLE.md

Commit subjects use the `[<scope>] Description` format, even though the older history uses unscoped subjects. The guide's linter, type-checker and test-runner steps map to `npm run lint` (ESLint with the Next core-web-vitals and TypeScript rules), `npm run typecheck` (strict `tsc`) and Vitest. Test files keep the `*.test.ts` suffix, because Vitest discovers them by it. Prettier (exact-pinned, configured in `.prettierrc.json`) is used only on newly authored files, checked with `npm run format:check -- <files>`; moved code stays byte-identical, so never run it over existing files. The global guide's "virtual environment" rule maps to installing packages locally with `npm` (never `-g`).

Name new TypeScript functions and variables in `snake_case`, as the global guide says, even though the existing code is camelCase. Don't rename existing identifiers. React has two exceptions: components must stay PascalCase, since JSX treats lowercase tags as DOM elements, and custom hooks must stay `useXxx`, since the rules-of-hooks lint only recognises that pattern.

The game is published as **Hawker Balance**. The repo, package, and IndexedDB names still say `hawker-simulator`. It requires Node.js 22.15 or newer. The `@/` import alias maps to the repo root, as in `@/src/game/core`. Don't edit the generated `.next/`, `dist/`, or `node_modules/` folders.

## Commands

```bash
npm run dev                                   # next dev on http://localhost:3000
npm run typecheck                             # tsc --noEmit
npm run lint
npm test                                      # all Vitest suites (tests/**/*.test.ts)
npx vitest run tests/game/core/lifecycle.test.ts   # single file
npx vitest run -t "partial test name"         # single test by name
npm run validate:content                      # content contract only
npm run format:check -- <files>               # Prettier check, for newly authored files only
npm run test:release                          # full gate: typecheck, lint, test, build, test:ssr
```

- `npm run test:ssr` imports `dist/server/index.js`, so it only works after `npm run build`.
- `npm run build` uses Vinext/Vite and writes to `dist/`, with `worker/index.ts` as the Cloudflare Worker entry. `npm run build:vercel` is a separate native `next build`. CI (`.github/workflows/vercel.yml`) runs `test:release`, then `build:vercel`, then `npm audit --omit=dev --audit-level=high`, which gates the dependencies that ship to players; `docs/TEST_REPORT.md#dependency-audit` records the all-dependencies result.
- Both builds first run `tools/stamp-service-worker.mjs`. It rewrites the `BUILD_ID` in the tracked `public/sw.js` with a hash of `app/`, `src/`, `public/`, and `package-lock.json`. Any source change followed by a build therefore modifies `public/sw.js`. Commit the restamped file together with the source change that caused it. The hash depends on the platform (path separators and sort order), so a Linux build and a Windows build stamp different IDs.
- `npm test` includes an 80-agent Node benchmark (`tests/game/core/performance.test.ts`) that prints `BENCHMARK_RESULT`. It does not measure browser rendering.
- **Test layout.** `tests/` mirrors the source tree: `tests/game/core/` (with `persistence/`), `tests/game/runtime/` (with `render/` and `visuals/`), `tests/game/persistence/`, `tests/game/audio/`, `tests/game/pwa/`, `tests/config/`, `tests/content/`, `tests/app/game/` and `tests/tools/nutrition/`. Repo-wide checks sit at the top level: `tests/module-docs.test.ts` requires a module JSDoc header on every `src/`, `app/`, `tools/` and `worker/` module (its baseline allowlist may only get shorter), and `tests/hosting-config.test.ts` checks the dual-target (Vinext/Cloudflare and Vercel) hosting configuration. Shared test helpers live in `fixtures.ts` files beside the suites that use them. Tests import source through `@/`. Put a regression test next to the closest existing suite.
- **Test environments.** Tests run in Vitest's Node environment. Suites that need a DOM opt in with `// @vitest-environment jsdom` (React Testing Library), and IndexedDB tests use `fake-indexeddb`. `tests/rendered-html.test.mjs` uses Node's own test runner instead.
- **Console output.** `tests/setup.ts` fails a test on any unexpected `console.warn`/`console.error` or Node process warning. If a test deliberately triggers one, declare it with `expect_console_warning` from `tests/console.ts`.
- **Goldens.** Golden suites, listed in `docs/TEST_PLAN.md`, pin the game's behaviour as sha256 literals and insertion-ordered snapshots. Run them with `CI=true` so a missing snapshot fails rather than being written. Change a golden only for an intentional behaviour or balance change, and say why in the commit.

## Architecture

### Layering (enforced by imports)

`eslint.config.mjs` enforces these rules and `npm run lint` runs with `--max-warnings=0`. The core rule and the `app/` bans on `runtime/render/*` and `runtime/visuals/vendor.ts` resolve every specifier, relative paths included (`import/no-restricted-paths`); the `app/` ban on a static (value) `createHawkerRuntime` import matches the `@/` alias only, since `app/game/hooks.ts` imports it dynamically.

1. **`src/content/`** holds the authored data (stalls, dishes, placeables, customers, localization, nutrition) as plain TS constants, plus the Zod schemas (`schemas.ts`, where every enumerated value set is a named schema such as `dishCategorySchema` or `nutritionClassSchema`), the content types (`types.ts`: each type, such as `StallDefinition`, is `ReadonlyDeep<z.output<typeof xSchema>>`, so the field comments live on the schema keys and only `ContentId` and `LocalizedSeed` are hand-written; `tests/content/types.test.ts` asserts each type equals its schema output), the launch roster (`roster.ts`: `LAUNCH_ROSTER`, the record counts, and `PLACEABLE_CATEGORY_MINIMUMS`, both re-exported from `index.ts`, plus the reference lists `VARIANT_UNLOCK_RANKS` and `NOT_COMPARABLE_GUIDELINE_IDS`) and the cross-reference validator. Each data file builds its records and English entries through the leaf `seeds.ts` (type-only imports: `build_localization_keys(id)`, which derives `<id>.name` and `<id>.description`, `strip_localized_copy` and `build_english_entries`). The data files name their balancing constants: `dishes.ts` the star-rating weights and serving-time factors (`STAR_QUALITY_WEIGHT`, `STAR_DEMAND_WEIGHT`, `SERVING_MS_PER_PREP_SECOND`, `MIN_SERVING_MS`), `placeables.ts` `RESALE_RATIO` and `DEFAULT_ROTATIONS`, and `stalls.ts` the upgrade ladder (`LEVEL_2_SERVICE_TIME_MULTIPLIER` to `LEVEL_4_SERVICE_TIME_MULTIPLIER`, `LEVEL_3_COST_FACTOR`, `LEVEL_4_COST_FACTOR`). `localization.ts` merges the entries into `ENGLISH_LOCALIZATION` in the order stalls, dishes, placeables, customers, throwing on a duplicate key, and exports `localize_key` (the `?? key` fallback lookup), of which the runtime's `localized` and the UI's `localize` are aliases. `nutrition.ts` exports `is_primary_profile`, which the profile lookup and the validator share. `validate.ts` holds `validateContent`, which parses the content with `launchContentSchema` and then runs the rule groups in `rules.ts` in a fixed order (`check_roster`, `check_identity_and_copy`, `check_stalls`, `check_dishes`, `check_nutrition`, `check_placeables`, which returns the category counts, `check_progression`, `check_economy`, which returns the starter bundle cost, and `check_customers`), each taking `(content, check)`; that order is the order of the reported issues. `rules.ts` names its thresholds (`MIN_NAME_LENGTH`, `MIN_DESCRIPTION_LENGTH`, `MIN_DISHES_PER_STALL`, `MIN_STARTER_STALLS`, `PLAUSIBLE_VISITS_PER_LEVEL`), and each check reports its own message. `LAUNCH_CONTENT` in `catalog.ts` is the bundle `validateContent` checks and carries the content version (`1.3.0`), which only the validation report records (the runtime builds its catalogs from the content modules directly), and `catalog.ts` also exports the shared `DISH_BY_ID`, `STALL_BY_ID` and `PLACEABLE_BY_ID` lookup maps (built in array order) that the runtime uses instead of building its own.
2. **`src/game/core/`** is the pure, deterministic simulation. It imports nothing outside itself: not content, Phaser, React, or browser APIs. Instead it receives a `SimulationCatalog` through `GameState.catalog`. Core tests use the small synthetic `TEST_CATALOG` in `tests/game/core/fixtures.ts`, not the real content. The barrel `core/index.ts` is the explicit public API: it re-exports only the names used outside core (plus every type in `types.ts`), so code outside core that needs an internal imports its module directly. The enumerated vocabularies (rotations, tile kinds, quality modes, queue directions, objective kinds, nutrition intents, metrics and health conditions, and so on) are ordered `as const` tuples in the leaf module `core/enums.ts`; `types.ts` derives its unions from them, the save loader checks persisted values against them, and `tests/content/schemas.test.ts` keeps the content Zod enums in step. `rng.ts` also owns `compute_fnv1a32`, the one FNV-1a loop shared by seed hashing and the `saveStore` checksum; the barrel re-exports it, but `saveStore.ts` imports `core/rng` directly so the eagerly loaded save store stays free of the core barrel. `pathfinding.ts` holds only the A* search (`findPath`, `isReachable`), and `navigation.ts` holds `validateWorldNavigationAccess`, the layout reachability check that commands and new-game setup run. The step simulation is split by concern: `simulation.ts` keeps only `stepSimulation` and `advanceSimulation`, and its module JSDoc documents the per-step RNG order and the contract that `processCustomer` returns `undefined` for a despawned customer; `lifecycle.ts` (internal) holds `processCustomer`, which dispatches through `CUSTOMER_STATUS_HANDLERS`, one handler per status checked with `satisfies Record<CustomerStatus, StatusHandler>` so a new status without a handler fails to compile, plus the shared recovery helpers `recover_to_stall_choice` and `recover_to_seat_search`; `visits.ts` (internal) holds `completeSale`, `settleVisitRating` and the visit-rating constants; `draft.ts` (internal, not in the barrel) holds the mutable step `Draft` and its primitives (events, status transitions, stall lookup, queue and seat bookkeeping, movement, exit choice and `beginExit`); `arrivals.ts` holds archetype spawn weighting, `spawnCustomer` and `compute_next_spawn_interval_ms` (the adaptive arrival model, called after the spawn); `choices.ts` holds stall, dish, seat and tray-return choice; and `diagnostics.ts` holds `assertSimulationInvariants`, `simulationDigest` and `stateDigest`. Command handling is split the same way: `commands.ts` keeps only `dispatchCommand`, which looks the command type up in `COMMAND_HANDLERS` (a mapped type over `GameCommand["type"]`, so a new command without a handler fails to compile, and an unknown type or an inherited key such as `toString` gets the "Unsupported command" rejection through `Object.hasOwn`), plus the settings, stall-upgrade and stall-open handlers; build commands wrap their handler in `with_undo_snapshot`, so the undo snapshot is captured before validation. The internal modules behind it are `build.ts` (one `handle_*` function per build command, each taking `(state, command, before)`), `undo.ts` (`withUndo` and `apply_undo`), `reconcile.ts` (`reconcileWorldTargets` and `reconcileWorldGeometryChange`, which repair guests, queues and seat reservations after a layout change) and `results.ts` (`accept`, `reject` and `commandEvent`). `validation.ts` checks catalog record shapes, then runs `validate_placeables`, `validate_dishes` and `validate_archetypes` in that order through the shared `check_record_identity` and `check_range` rules. Each module keeps its own tuning constants.
3. **`src/game/runtime/createHawkerRuntime.ts`** is the single composition root (~670 lines). It loads saves through `load_runtime_save` (logging each discarded save candidate and the final recovery error with `console.warn`), lazy-imports Phaser (only `import type Phaser` at the top level), and builds the scene class with `create_scene_class` and the game with `create_game` (both in `render/scene.ts`), passing the scene its `SceneBindings`. It returns a `RuntimeController` (`runtime/types.ts`) and pushes `RuntimeSnapshot`s and events back through callbacks. The root keeps its HUD and autosave cadence as named constants (`HUD_INTERVAL_MS`, `PERIODIC_SAVE_INTERVAL_MS`), and owns the frame step `advance_frame` (the former scene `update()` body, with its statement order and `performance.now()` reads unchanged, kept in the root because the guest-cleanup event and those reads sit between the domain updates), the key switch `handle_key`, `build_render_context`, `emitHud`, the controller, and `runCommand`, whose side-effect order is fixed: dispatch, then menu sync (both through `dispatch_session_command`), then `onEvent`, then persist, then render, then `emitHud`. The live game data sits in one `RuntimeSession` (`session.ts`: authored catalog, visuals, layered catalog, state, stall menus, active dish variants, and the save bookkeeping `lastPersistentRevenue`, `lastPeriodicSaveAt` and `lastSimulationMs`), which the root creates once with `create_runtime_session` and never replaces; `session.ts` also holds `adopt_session` (startup, import and reset adopt a whole loaded or fresh session from `load_runtime_save` or `create_fresh_session`), `apply_catalog_layers` (called whenever the menus or variants change, it updates `catalog` and `state.catalog` together), `synchronize_stall_menus`, `build_persistent_payload` (the runtime save envelope) and `dispatch_session_command`, which returns `{ accepted, events, hasMenusChanged }`. The selection, pending move, queue draft, access-point, cursor, speed and ID-sequence state sits in one `InteractionState` (`interaction.ts`), created once by `create_interaction_state(state)` and mutated in place; `interaction.ts` also holds the tile handler `handleTile` and the setters `setBuildTool`, `rotateSelection` and `setSpeed`, which take an `InteractionContext` (`getSessionState()`, `getCatalog()`, `isReducedMotion()`, the interaction state, `runCommand`, `emitHud`, `render` and `emitEvent`) and call its getters at each use, plus the pure hit tests and ID helpers `customerAtRenderedGridPoint` (re-exported from the root), `objectAt`, `customerAt`, `placementCandidate`, `nextObjectId` and `recomputeObjectSequence`. Each HUD push assembles a fresh `SnapshotInput` and calls `build_runtime_snapshot`. The pure, Phaser-free helpers it composes live beside it: `catalog.ts` converts content into a `SimulationCatalog` (`buildCatalog`, with its stall and placeholder projection numbers as named constants), layers the player's stall menus and active dish variants on top (`layer_catalog`, which is `withStallMenus(withDishVariants(...))`) and applies stall upgrades (`effectiveCatalog(state, catalog)`); `world.ts` holds the launch map constants (`TILE_SIZE`, `MAP_WIDTH`, `MAP_HEIGHT`, `ACCESS_ROW`, `LAUNCH_SEED`), the `STARTER_LAYOUT`, `freshState`, `create_fresh_session` (the fresh state with default menus and variants layered on, used by startup without a usable save, save recovery and reset), `assertRuntimeMap` and `reconcileRuntimeUnlocks` (the reputation and prerequisite unlock rules applied between frames, which stay out of core because they come from content); `rules.ts` is an import-free leaf holding the rule constants the runtime and the HUD share (`REPUTATION_SCALE`, the content-to-core reputation ratio, and `MAP_EXPANSION`, the expansion size and minimum level), kept separate so the eager HUD chunk does not pull in the catalog projection or new-game setup; `nutrition.ts` holds the content-to-core nutrition profile copy, HUD nutrition summaries, customer decision reasons, `compute_dish_mastery_rank` (the best mastery rank among a dish's stalls, which gates variants), dish-variant defaults and resolution, and the nutrition parts of the HUD snapshot (`build_nutrition_families`, `build_nutrition_pulse`, `build_customer_nutrition`); `stallMenus.ts` holds menu selection and resolution plus `compute_menu_slots` (used by the runtime and the HUD), `stallMenuProgression`, `stallMenuSlotBonuses` and `stallMenusMatch`; `activityFeed.ts` holds `formatSimulationEvent` (simulation event to HUD event), popup and grouping rules; `saves.ts` holds the runtime save envelope (`RuntimePersistentState`, `RUNTIME_SCHEMA_VERSION`, `decodeRuntimeSave`, `resolvePersistedDishVariants`) and `load_runtime_save`, the one load pipeline startup and import share (decode, deserialise, map check, unlock reconcile, menu and variant resolution, catalog layering), which returns `isRecovered` and leaves the per-path messages to its callers; and `snapshot.ts` holds `build_runtime_snapshot`, the pure HUD snapshot projection of a `SnapshotInput` (state, catalog layers, interaction state, fps and simulation time), plus `isCentreOpen(state, catalog)`, the HUD clock label and focused projection helpers (`resolve_queue_direction`, `build_milestone_tracks` (from core's `MILESTONE_TRACKS`, with variety from `distinctOpenStallTypes`), `get_main_guest_route`, and `estimate_hall_cleanliness`, a HUD-only heuristic with named coefficients that never feeds the visit ratings); it also reads `requiredRank` from core's `UPGRADE_RANK_REQUIREMENTS`. The procedural-art recipes live in `runtime/visuals/`: `palette.ts` holds the shared colour helpers (`colour`, `mixColour`, `lighten`, `darken`), `stableVisualHash` and the `ACCENTS`, `SKIN_TONES` and `CLOTHING` palettes; `placeable.ts` holds `visualRecipeForPlaceable` and its types; `dish.ts` holds `visualRecipeForDish`, `visualRecipeForDishVariant` and `variantVisualFamilyForKey`; `customer.ts` holds the customer archetype recipes, `customerAppearanceForId`, `animationPoseForCustomer` and `CUSTOMER_INDICATOR_LEGEND` (the HUD imports the legend); and `vendor.ts` holds the stall-vendor recipes and `vendorAnimationPoseForStall`, which only the lazily loaded runtime may import (app/ is blocked by lint). The renderers live in `runtime/render/`, import Phaser as a type only, and (apart from `scene.ts`, which holds the scene) never touch the scene: they read only their arguments, usually a `RenderContext`. `context.ts` holds the shared `LabelSink` (a label callback the scene builds from its `addLabel`) and `ObjectVisualBounds` types, plus `RenderFrame` (tick, quality, reduced motion, high contrast), `RenderContext` (the frame, snapshot, live state, layered catalog, visuals, menus, variants, selection, debug flag and `addLabel`) and `OverlayContext` (adding the effective catalog, build tool, selected build ID, hover tile and `placementCandidate`); the root's `build_render_context` builds one `OverlayContext` (a `RenderContext` plus the build interaction state) per render, taking `tick` from the snapshot and quality from the runtime's own setting. `scene.ts` holds `create_scene_class(phaser, bindings)`, which builds `HawkerScene` (scene key `hawker-centre`) on the dynamically imported Phaser namespace, `create_game`, the `SceneBindings` and `HawkerSceneHandle` types, and the frame, camera and FPS constants (`MAX_FRAME_DELTA_MS`, `CAMERA_MIN_ZOOM`/`CAMERA_MAX_ZOOM`, `STANDARD_FPS_LIMIT`/`LOWER_END_FPS_LIMIT`); the scene owns only its graphics, labels, drag-pan fields, frame clock and last drawn tick, delegates stepping, tiles and keys to the root, and draws in the order `drawMap`, `drawObjects`, `drawCustomers`, then `drawOverlay`. `map.ts` holds `drawMap` (tiles, route guides, the predicted guest route and the access-point portals); `overlay.ts` holds `drawOverlay` (queue paths and counts, reserved seats, the build-tool hover preview and the debug footprints); `objects.ts` holds `boundsForObject(object, catalog)`, the `drawObjects` dispatch, which sends stalls to `drawStallGraphic` and every other object through `OBJECT_RENDERERS` (a `Record<PlaceableCategory, ObjectRenderer>`), and the non-stall object renderers (table, seat, fixture, tray-waste, lighting, fan, facility, plant, signage, divider and decor graphics, plus `drawMakerMark` and `drawObjectShadow`); the fan blades turn by `degrees * DEG_TO_RAD`, the same form as Phaser's `DegToRad`; `stall.ts` holds `drawStallGraphic`, `drawStallEmblem`, `stallServiceVisualState` and `displayDishIdsForStall` (the counter food-prop selection), and `objects.ts` and `stall.ts` import each other, for functions only; `art.ts` (a pure leaf) holds the ID-keyed art tables `STALL_ART_BY_ID` (each stall's roofline and counter work-prop branch) and `PLACEABLE_STYLE_BY_ID` (keyed by category, then content ID: each placeable's branch in its category renderer, with tables and signs recording two independent branches), whose literals record the branch each launch ID reached through the renderers' former substring chains; `drawStallGraphic` and the object renderers select their branch through `resolve_stall_art` and `resolve_placeable_style`, which read the table first (through `Object.hasOwn`) and fall back to those substring chains (`classify_stall_art`, `classify_placeable_style`) for unlisted IDs, while single-substring cues on the motif still tweak sizes, colours and details within a branch, and `tests/game/runtime/render/art.test.ts` requires an explicit entry for every STALLS and PLACEABLES ID; `dishes.ts` holds `drawDishServing` (vessel, food motif, variant cue and steam) and its internal motif helpers, used by stall counters and customers; `vendor.ts` holds `drawStallVendor` and the vendor hair, headwear and tool renderers; `variants.ts` holds `drawNutritionVariantCue` (the per-family nutrition variant cue drawn on a served dish) and `includes_any`, the substring test its cue choices and the dish motif choices use; and `customers.ts` holds `drawCustomers`, its `nearestTableMealAnchor` helper, `renderedCustomerPosition` (also used by the `customerAtRenderedGridPoint` hit test in `runtime/interaction.ts`) and the customer leaf renderers `drawCustomerIndicator`, `drawCustomerAccessory`, `customerOutfitDimensions` and `drawCustomerGarmentPattern`. app/ may not import `runtime/render/*`. The other `runtime/*.ts` helpers (queue/satisfaction insights) are pure too, and have their own tests.
4. **`app/game/HawkerSimulator.tsx`** is a `"use client"` component of about 930 lines: the shell that owns the UI state, which modal is open, the focus traps and the callbacks, and composes the HUD, panel and dialog components below. It renders every essential control as semantic DOM and handles saving through `src/game/persistence/saveStore.ts`. Phaser never creates essential DOM controls, and React never mutates simulation entities. Its wiring to everything outside React lives in `app/game/hooks.ts`: `useAnnouncer` (the toasts, the activity feed and its unread count, and the one-shot storage warning; `announce` and `reportStorageIssue` are stable), `usePreferenceWriter` (returns `persist_preference(key, value, failure_message)`, which every preference write goes through), `useAutosave` (creates the autosave queue lazily through a ref), `useHawkerRuntime` (the startup effect, with an empty dependency list, latest-value callback refs and the `disposed` flag: it reads preferences and saves, lazy-imports the runtime, creates the `AudioDirector`, registers the PWA, flushes the autosave on `pagehide` and unmount, and returns the controller and audio refs and the loading state) and `report_failure(context, error)`, which logs a handled UI failure with `console.warn("[ui] <context>", error)`. The component calls `useHawkerRuntime` before its settings effect, because the runtime effect's first statement issues the stored settings read, so IndexedDB queues it ahead of the mount's write of the defaults (TD-08). `app/game/display.ts` holds the pure view helpers (`money` with its hoisted `SGD_FORMATTER`, `localize`, `unlockLabel`, `utilityEffects`, `primaryUtility`, `catalogueIcon`, `getContentPrice`, `placeablePreview`, `dishPreview`, `dishLabel`, `dishStarRating`, `personaLabel`, `nutritionProfileView`, `CUSTOMER_PERSONAS_BY_UNLOCK`, `BUILD_CATEGORIES`, the `Panel` type and `PANEL_COPY`) plus the helpers several surfaces share: `format_progress_percent` (the level, objective and progress bar widths), `format_hex_colour` (the preview colours), `humanize_id(id, { prefix, shouldReplaceAll })` (content labels replace every hyphen, the category chips and dish rows only the first), `is_requirement_met(requirement, snapshot)` (the persona count, persona roster and dish gating) and the per-surface `TOAST_KIND_GLYPHS` and `ACTIVITY_KIND_GLYPHS`; the initial HUD snapshot takes its cash and reputation from `ECONOMY`. `app/game/focus.ts` holds the focus handling: the exact `MODAL_FOCUSABLE_SELECTOR`, `SHEET_FOCUSABLE_SELECTOR` and `VARIANT_LAB_FOCUSABLE_SELECTOR`, `dialogFocusAction` (re-exported from `NutritionEducation.tsx`), `TUTORIAL_DONE_STEP` (`TUTORIAL_COPY` in `dialogs.tsx` is checked to have that many cards) and `NUTRITION_TOUR_DONE_STEP` with their step types `TutorialStep` and `NutritionTourStep`, `resolve_active_modal` (Reset, then Settings, then Help, then the tutorial, then the nutrition tour) and `is_interface_inert` (any of those or the Variant Lab), and `install_focus_trap(container, options)`, which the modal dialogs, the compact management sheet and the Variant Lab call from their own `useEffect` with their own dependency lists and return as the cleanup; The Settings switches and sliders are `SettingSwitch` and `SettingSlider`, which call the shell's `update_setting(key, value)` through `onUpdateSetting`. `app/game/panels/catalogue.tsx` holds the presentational `BuildPanel`, `StallsPanel` and `SelectionCard`, moved from the shell with their markup unchanged (shared formatters from `display.ts` replaced inline expressions); the amber dot marks the tools in `TOOLBAR_MODE_LABELS`), `ActionStrip`, `BottomDock` (its tabs are `DOCK_ITEMS`), `ToastStack` and `DebugPanel` (the shell keeps its open state and renders it only when the debug flag is set). The shell passes `isInert` to each surface that carries the `inert` and `aria-hidden` pair; the connection badge stays inline in the shell. `nutritionProfileView` is `runtimeNutritionProfile(coreNutritionProfile(getNutritionProfile(...)))` from `runtime/nutrition.ts`, and `NutritionEducation.tsx` takes `HEALTH_CONDITION_LABELS` from there too, keeping only its intent labels as UI copy. The persistence helpers it uses are React-free and tested in Node: `persistence/preferences.ts` holds the four persisted preference keys (`PREFERENCE_KEYS`, whose `PreferenceKey` type narrows `savePreference` and `loadPreference`), `DEFAULT_SETTINGS`, `normalizeSettings` (with its literal fallbacks and the legacy ambience-to-music fallback), `load_player_preferences(load, read_initial_settings)` (issues the settings read synchronously, then the other three reads in order, and returns `{ values, error }`, keeping every value read before a rejection), the text scale range, `DEFAULT_MIX` and `get_voice_limit_for_quality` (which `AudioDirector` also reads for its initial mix and voice limit); `persistence/autosave.ts` holds `create_autosave`, the debounced (200 ms), serialised save queue (`schedule`, `flush`, `save`, `cancel`, `settle`) that reports status for the latest write only, logs each failed write with `console.warn("[autosave] write failed", error)` and rejects `save` with `Error("Local save failed", { cause })`. `saveStore.ts` also owns `build_save_file_name(day)`, the exported file name.

`docs/README.md` indexes the docs and names the single owner of each volatile fact: content counts in `docs/CONTENT_CATALOGUE.md`, test evidence in `docs/TEST_REPORT.md`, and release blockers, pinned behaviour defects and deferred debt in `docs/KNOWN_ISSUES.md`; other docs link to the owner instead of copying the value, apart from the launch-count acceptance criteria that `docs/README.md` lists as restated. `docs/TECHNICAL_DESIGN.md` describes this layout (its domain layout, layering rules, save sequence, update gating and debug flags) and must name only `src/` and `app/` paths that exist. `docs/SAVE_FORMAT.md` records the save version nesting, the V1-V4 history and the persistence invariants, with checklists for adding a schema version or a persisted field. `docs/TECH_DEBT.md` holds the scored tech-debt register, the partial refactor steps and the open follow-ups; update an item's status there when you resolve it.

### Core simulation model

- State is immutable. `dispatchCommand(state, command)` returns `{ state, accepted, error?, events }`. Commands validate everything before they mutate anything. A rejection returns `accepted: false` and leaves the gameplay state as it was.
- `advanceSimulation(state, realDeltaMs)` accumulates real time into fixed steps (`config.fixedStepMs`, 10 Hz). It caps the steps per call by quality mode and drops the excess. `stepSimulation` advances exactly one tick, and `updateProgressionSystems` runs at the end of every step.
- Randomness is threaded explicitly: `GameState.rngState` passes through the pure functions in `rng.ts`, which return `{ value, state }`. Never use `Math.random`, wall-clock time, or `localeCompare` in core. Use `compareIds` (`ordering.ts`) for any ID ordering that affects results.
- `simulationDigest` / `stateDigest` and `assertSimulationInvariants` exist for determinism and soak tests. Any change to core behaviour should keep the seeded runs reproducible.
- Customers, queues, and reservations exist only at runtime and are not saved. Map, objects, economy, progression, route guides, access points, visit and nutrition metrics, `rngState`, and `elapsedMs` are saved.

### Persistence has three version layers

1. `core/persistence/` is a folder module, imported as `./persistence`. `PERSISTENT_SCHEMA_VERSION` (currently 4) lives in the leaf `core/enums.ts`, so `state.ts` and `types.ts` can use it without an import cycle, and `persistence/index.ts` re-exports it. `index.ts` also holds serialisation and `deserializeGameStateWithReport`, which validates the migrated save against the catalog. `fields.ts` holds the primitive field readers and `PersistenceError` (it must not import `index.ts`), `parsers.ts` the section parsers (the lifetime and today nutrition metrics share the per-intent, per-nutrient and per-dish readers, with prefix-built error paths), `migrations.ts` one `parseVN` per schema version plus the `upgrade_vN_to_vN+1` chain that `migratePersistentState` walks (parse, upgrade, re-parse), and `recovery.ts` the alias and refund recovery of objects and unlocks. In `core/nutrition.ts`, the empty nutrition metrics and their clone share `build_intent_metrics_record`, `build_metric_record` and `clone_day_metrics`, so a new nutrition counter touches one builder and one cloner. The nutrition-metric bookkeeping for a step also lives there: `record_intent_request` (called through `recordIntentRequest` in `arrivals.ts`) and `record_nutrition_sale` (called by `completeSale`, after the request), both pure functions of the metrics and the operating day.
2. The runtime save wrapper (`decodeRuntimeSave` in `runtime/saves.ts`, `runtimeSchemaVersion` 1|2, where `RUNTIME_SCHEMA_VERSION` = 2 is the version written) adds stall menus, dish variants, and `nutritionDataVersion`. If the saved nutrition data version doesn't match the current one, variant choices reset to reviewed defaults.
3. `persistence/saveStore.ts` stores IndexedDB envelopes (`saveVersion`, checksum) in `active` and `backup` slots. At load, the runtime tries each saved candidate in order through `load_runtime_save` and falls back to a new centre.

A change to saved shape needs a version bump at the right layer, a migration, a new frozen fixture in `tests/game/core/persistence/fixtures/`, and a test (see `tests/game/core/persistence/migrations.test.ts`).

### Content and nutrition contracts

- `validateContent` enforces the launch counts in `LAUNCH_ROSTER` (`src/content/roster.ts`): exactly 14 stalls, 54 dishes, 12 archetypes, 2 nutrition source snapshots, 14 nutrition variant families, 5 intents and 11 guidelines, at least 80 placeables, and a nutrition profile total derived as one per dish plus one per non-default variant (104 today), along with localization completeness. The Zod schemas only require these lists to be non-empty. To add or remove content, update `LAUNCH_ROSTER` (and `NUTRITION_GUIDELINE_COUNT` in `tools/nutrition/manifest.mjs` for guidelines; a test keeps the two in step), the localization entries, the "Roster counts" table in `docs/CONTENT_CATALOGUE.md`, and the documents that `docs/README.md` lists as restating those counts.
- `src/content/nutrition.generated.json` is generated, so don't hand-edit it. It comes from `tools/nutrition/importer.mjs`, which uses the authored exact mappings in `tools/nutrition/manifest.mjs` and operator-supplied CSVs in the git-ignored `data/` folder (see `docs/NUTRITION_DATA.md` for the command). Raw CSVs are never committed, and CSV parsing or fuzzy matching never runs in the browser. The importer delegates CSV parsing and row hashing to `tools/nutrition/csv.mjs` (`parseCsv`, `canonicalRowHash`, `sha256`) and the rating passes to `tools/nutrition/ratings.mjs` (`HEALTH_RATING_SCHEMES`, `computeRelativeFits`, `nutritionValueForComparison`, `addIntentFits`, `addHealthRatings`), re-exporting the public names (`parseCsv`, `canonicalRowHash` and the five rating names) so callers keep one entry point, and names its quarantine thresholds (`COMPONENT_TOLERANCE_G`, `MAX_MACRONUTRIENT_SERVING_RATIO`, the energy cross-check ratios and the manual-review limits). All four files are `// @ts-check` with JSDoc types from `src/content/types` and are listed in the `tsconfig.json` include, so `npm run typecheck` checks them; `checkJs` stays off globally.
- Dishes have two independent ratings: the Star rating (taste and popularity, authored) and the Health and condition ratings (relative nutrient fit, generated). Health conditions must stay independent of customer personas and demographics. UI copy must not label dishes good or bad or make medical claims.

### Hosting and security

- Response headers live only in `src/config/securityHeaders.ts`, which both `next.config.ts` and `worker/index.ts` consume. The CSP is `connect-src 'self'`.
- Build mode and the developer `?debug` / `?visualQa` query flags are read only through `src/config/env.ts` (`IS_PRODUCTION_BUILD`, `IS_DEVELOPMENT_BUILD`, `has_dev_query_flag`). Call sites test `!IS_PRODUCTION_BUILD` before `has_dev_query_flag` so Vite drops the developer-only branches from production bundles. `vite.config.ts` and `tools/*.mjs` run in Node and are the documented exceptions.
- By design there is no backend, account, analytics, telemetry, or payment, and gameplay doesn't depend on the network (ADR 0003). The service worker and its save-gated update flow live in `public/sw.js` and `src/game/pwa/registerPwa.ts`, which owns the page-to-worker protocol (`SW_MESSAGE`, `WARM_CACHE_TIMEOUT_MS`) and `activate_waiting_update`; the component saves first and calls it only when the save succeeds.

## Docs conventions

- `docs/DECISIONS.md` requires a new ADR in `docs/adr/` for any reversal that affects persistence, content IDs, rendering perspective, offline behaviour, the accessibility boundary, or release compatibility. Balance tweaks go in `CHANGELOG.md` instead.
- The docs deliberately avoid calling the build production-approved, and edits must keep it that way. Package and cache version numbers do not indicate release state.

## Pull requests

A PR description should explain the impact on players or operations, list the validation commands that were run, and link any relevant issues. Include screenshots for visible UI changes. Call out anything that affects deployment, persistence, accessibility, or security.
