# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Standards

Follow the coding and commit standards below. They are copies of the user's global style guides, kept in the repo so that cloud sessions have them too.

@context/CODING_STYLE.md

@context/COMMIT_STYLE.md

Author and commit every commit as the repo owner, `Adison Goh <adisongoh88@u.nus.edu>` (set `git config user.name` and `user.email` in a fresh clone before the first commit), never as Claude, and leave out any `Co-Authored-By: Claude` or `Claude-Session:` trailer, whatever a tool or harness default suggests.

Commit subjects use the `[<scope>] Description` format, even though the older history uses unscoped subjects. The guide's linter, type-checker and test-runner steps map to `npm run lint` (ESLint with the Next core-web-vitals and TypeScript rules), `npm run typecheck` (strict `tsc`) and Vitest. Test files keep the `*.test.ts` suffix, because Vitest discovers them by it. Prettier (exact-pinned, configured in `.prettierrc.json`) is used only on newly authored files, checked with `npm run format:check -- <files>`; moved code stays byte-identical, so never run it over existing files. The global guide's "virtual environment" rule maps to installing packages locally with `npm` (never `-g`).

Name new TypeScript functions and variables in `snake_case`, as the global guide says, even though the existing code is camelCase. Don't rename existing identifiers. React has two exceptions: components must stay PascalCase, since JSX treats lowercase tags as DOM elements, and custom hooks must stay `useXxx`, since the rules-of-hooks lint only recognises that pattern.

The game is published as **Hawker Balance**. The repo, package, and IndexedDB names still say `hawker-simulator`. It requires Node.js 22.15 or newer. The `@/` import alias maps to the repo root, as in `@/src/game/core`. Don't edit the generated `.next/`, `dist/`, or `node_modules/` folders.

## Commands

```bash
npm run dev                                   # next dev on http://localhost:3000
npm run typecheck                             # tsc --noEmit
npm run lint
npm test                                      # all Vitest suites (tests/**/*.test.ts)
npx vitest run tests/game/core/lifecycle.test.ts   # single file
npx vitest run -t "partial test name"         # single test by name
npm run validate:content                      # content contract only
npm run format:check -- <files>               # Prettier check, for newly authored files only
npx tsx tools/paint-gallery.ts --kind stalls --out scratch/stalls.png   # PNG contact sheet of a painter kind
npm run test:release                          # full gate: typecheck, lint, test, build, test:ssr
```

- `npm run test:ssr` imports `dist/server/index.js`, so it only works after `npm run build`.
- `npm run build` uses Vinext/Vite and writes to `dist/`, with `worker/index.ts` as the Cloudflare Worker entry. `npm run build:vercel` is a separate native `next build`. CI (`.github/workflows/vercel.yml`) runs `test:release`, then `build:vercel`, then `npm audit --omit=dev --audit-level=high`, which gates the dependencies that ship to players; `docs/TEST_REPORT.md#dependency-audit` records the all-dependencies result.
- Both builds first run `tools/stamp-service-worker.mjs`. It rewrites the `BUILD_ID` in the tracked `public/sw.js` with a hash of `app/`, `src/`, `public/`, and `package-lock.json`. Any source change followed by a build therefore modifies `public/sw.js`. Commit the restamped file together with the source change that caused it. The hash depends on the platform (path separators and sort order), so a Linux build and a Windows build stamp different IDs.
- `npm test` includes an 80-agent Node benchmark (`tests/game/core/performance.test.ts`) that prints `BENCHMARK_RESULT`. It does not measure browser rendering.
- **Test layout.** `tests/` mirrors the source tree: `tests/game/core/` (with `persistence/`), `tests/game/runtime/` (with `art/`, `render/` and `visuals/`), `tests/game/persistence/`, `tests/game/audio/`, `tests/game/pwa/`, `tests/config/`, `tests/content/`, `tests/app/game/` and `tests/tools/nutrition/`. Repo-wide checks sit at the top level: `tests/module-docs.test.ts` requires a module JSDoc header on every `src/`, `app/`, `tools/` and `worker/` module (its baseline allowlist may only get shorter), and `tests/hosting-config.test.ts` checks the dual-target (Vinext/Cloudflare and Vercel) hosting configuration. Shared test helpers live in `fixtures.ts` files beside the suites that use them. Tests import source through `@/`. Put a regression test next to the closest existing suite.
- **Test environments.** Tests run in Vitest's Node environment. Suites that need a DOM opt in with `// @vitest-environment jsdom` (React Testing Library), and IndexedDB tests use `fake-indexeddb`. `tests/rendered-html.test.mjs` uses Node's own test runner instead.
- **Console output.** `tests/setup.ts` fails a test on any unexpected `console.warn`/`console.error` or Node process warning. If a test deliberately triggers one, declare it with `expect_console_warning` from `tests/console.ts`.
- **Goldens.** Golden suites, listed in `docs/TEST_PLAN.md`, pin the game's behaviour as sha256 literals and insertion-ordered snapshots. Run them with `CI=true` so a missing snapshot fails rather than being written. Change a golden only for an intentional behaviour or balance change, and say why in the commit. The render digests in `tests/game/runtime/createHawkerRuntime.render.test.ts` cover the painters' canvas calls and the retained sprite calls, so an intentional art change moves them; the painter suites in `tests/game/runtime/art/` check that every content item paints, paints deterministically and paints differently from its neighbours.

## Architecture

### Layering (enforced by imports)

`eslint.config.mjs` enforces these rules and `npm run lint` runs with `--max-warnings=0`. The core rule and the `app/` bans on `runtime/render/*` and `runtime/visuals/vendor.ts` resolve every specifier, relative paths included (`import/no-restricted-paths`); the `app/` ban on a static (value) `createHawkerRuntime` import matches the `@/` alias only, since `app/game/hooks.ts` imports it dynamically.

1. **`src/content/`** holds the authored data (stalls, dishes, placeables, customers, localization, nutrition) as plain TS constants, plus the Zod schemas (`schemas.ts`, where every enumerated value set is a named schema such as `dishCategorySchema` or `nutritionClassSchema`), the content types (`types.ts`: each type, such as `StallDefinition`, is `ReadonlyDeep<z.output<typeof xSchema>>`, so the field comments live on the schema keys and only `ContentId` and `LocalizedSeed` are hand-written; `tests/content/types.test.ts` asserts each type equals its schema output), the launch roster (`roster.ts`: `LAUNCH_ROSTER`, the record counts, and `PLACEABLE_CATEGORY_MINIMUMS`, both re-exported from `index.ts`, plus the reference lists `VARIANT_UNLOCK_RANKS` and `NOT_COMPARABLE_GUIDELINE_IDS`) and the cross-reference validator. Each data file builds its records and English entries through the leaf `seeds.ts` (type-only imports: `build_localization_keys(id)`, which derives `<id>.name` and `<id>.description`, `strip_localized_copy` and `build_english_entries`). The data files name their balancing constants: `dishes.ts` the star-rating weights and serving-time factors (`STAR_QUALITY_WEIGHT`, `STAR_DEMAND_WEIGHT`, `SERVING_MS_PER_PREP_SECOND`, `MIN_SERVING_MS`), `placeables.ts` `RESALE_RATIO` and `DEFAULT_ROTATIONS`, and `stalls.ts` the upgrade ladder (`LEVEL_2_SERVICE_TIME_MULTIPLIER` to `LEVEL_4_SERVICE_TIME_MULTIPLIER`, `LEVEL_3_COST_FACTOR`, `LEVEL_4_COST_FACTOR`). `localization.ts` merges the entries into `ENGLISH_LOCALIZATION` in the order stalls, dishes, placeables, customers, throwing on a duplicate key, and exports `localize_key` (the `?? key` fallback lookup), of which the runtime's `localized` and the UI's `localize` are aliases. `nutrition.ts` exports `is_primary_profile`, which the profile lookup and the validator share. `validate.ts` holds `validateContent`, which parses the content with `launchContentSchema` and then runs the rule groups in `rules.ts` in a fixed order (`check_roster`, `check_identity_and_copy`, `check_stalls`, `check_dishes`, `check_nutrition`, `check_placeables`, which returns the category counts, `check_progression`, `check_economy`, which returns the starter bundle cost, and `check_customers`), each taking `(content, check)`; that order is the order of the reported issues. `rules.ts` names its thresholds (`MIN_NAME_LENGTH`, `MIN_DESCRIPTION_LENGTH`, `MIN_DISHES_PER_STALL`, `MIN_STARTER_STALLS`, `PLAUSIBLE_VISITS_PER_LEVEL`), and each check reports its own message. `LAUNCH_CONTENT` in `catalog.ts` is the bundle `validateContent` checks and carries the content version (`1.6.0`), which only the validation report records (the runtime builds its catalogs from the content modules directly), and `catalog.ts` also exports the shared `DISH_BY_ID`, `STALL_BY_ID` and `PLACEABLE_BY_ID` lookup maps (built in array order) that the runtime uses instead of building its own. `calendar.ts` holds the neighbourhood day cards (`CALENDAR_CARDS`, `CALENDAR_CARD_BY_ID`: a fixed opening day plus nine bag cards), parsed with `calendarCardSchema` at import; their English copy lives on each card, not in `ENGLISH_LOCALIZATION`, they are not in `LAUNCH_ROSTER` or `LAUNCH_CONTENT`, and `tests/content/calendar.test.ts` validates them.
2. **`src/game/core/`** is the pure, deterministic simulation. It imports nothing outside itself: not content, Phaser, React, or browser APIs. Instead it receives a `SimulationCatalog` through `GameState.catalog`. Core tests use the small synthetic `TEST_CATALOG` in `tests/game/core/fixtures.ts`, not the real content. The barrel `core/index.ts` is the explicit public API: it re-exports only the names used outside core (plus every type in `types.ts`), so code outside core that needs an internal imports its module directly. The enumerated vocabularies (rotations, tile kinds, quality modes, queue directions, objective kinds, nutrition intents, metrics and health conditions, and so on) are ordered `as const` tuples in the leaf module `core/enums.ts`; `types.ts` derives its unions from them, the save loader checks persisted values against them, and `tests/content/schemas.test.ts` keeps the content Zod enums in step. `rng.ts` also owns `compute_fnv1a32`, the one FNV-1a loop shared by seed hashing and the `saveStore` checksum; the barrel re-exports it, but `saveStore.ts` imports `core/rng` directly so the eagerly loaded save store stays free of the core barrel. `pathfinding.ts` holds only the A* search (`findPath`, `isReachable`), and `navigation.ts` holds `validateWorldNavigationAccess`, the layout reachability check that commands and new-game setup run. The step simulation is split by concern: `simulation.ts` keeps only `stepSimulation` and `advanceSimulation`, and its module JSDoc documents the per-step RNG order and the contract that `processCustomer` returns `undefined` for a despawned customer; `lifecycle.ts` (internal) holds `processCustomer`, which dispatches through `CUSTOMER_STATUS_HANDLERS`, one handler per status checked with `satisfies Record<CustomerStatus, StatusHandler>` so a new status without a handler fails to compile, plus the shared recovery helpers `recover_to_stall_choice` and `recover_to_seat_search`; `visits.ts` (internal) holds `completeSale`, `settleVisitRating` and the visit-rating constants; `draft.ts` (internal, not in the barrel) holds the mutable step `Draft` and its primitives (events, status transitions, stall lookup, queue and seat bookkeeping, movement, exit choice and `beginExit`); `arrivals.ts` holds archetype spawn weighting, `spawnCustomer` and `compute_next_spawn_interval_ms` (the adaptive arrival model, called after the spawn); `choices.ts` holds stall, dish, seat and tray-return choice (`findSeat` skips seats holding a tray; stall and dish choice add today's card's category appeal and the Writer's Pick popularity bonus); `rush.ts` holds the time-of-day demand curve (`BASE_TIME_DEMAND` plus the biweight `LUNCH_RUSH` and `DINNER_RUSH` bumps, `compute_time_demand`, `active_rush_window` with `RUSH_CORE_SHARE`, inside which `arrivals.ts` halves the crowding backpressure) and last orders (`LAST_ORDERS_MINUTE` = 18:10, `is_last_orders`, which `is_arrival_window_closed` in `arrivals.ts` applies to the adaptive model only); `clearing.ts` (internal; only `count_cleaning_crew` and `get_worked_tray_keys`, the seat keys of the trays the crew is working on, which the renderer's visible crew reads, are in the barrel) holds the tray-return decision (`is_tray_returner`, an FNV-1a hash of the guest's ID against the archetype's `trayReturnChance`, plus a reachable return within `TRAY_RETURN_MAX_PATH_TILES` = 14, checked in `lifecycle.ts`), `leave_tray`, `compute_uncleared_neighbour_penalty` and `advance_table_clearing`, the crew of `BASE_CLEANING_CREW` plus one per tray-return station clearing the oldest trays first (`TRAY_CLEAR_MS`, faster near cleaning efficiency) in the runtime-only `GameState.unclearedTrays` (keyed by seat key, included in `stateDigest`, not saved); `neighbourhood.ts` holds the seeded neighbourhood in the optional `GameState.neighbourhood` (undefined in the core goldens and any core test that passes no `worldSeed` to `createNewGame`, always set by the runtime, saved from V5): `day_stream`, the shuffle-bag `draw_calendar_card` weighted by `compute_card_weight` from the director `tension`, `create_neighbourhood`, `compute_rush_windows` (seeded jitter plus today's card), the card lookups `get_today_card`, `get_archetype_factor` and `get_category_appeal`, the food writer (`is_writer_sample`, `settle_writer_review`, `compute_writer_threshold`, `get_writer_pick_bonus`), the day ledger (`start_day_ledger`, `record_visit`, called from `settleVisitRating`) and the rollover (`build_day_report`, `compute_day_performance`, `roll_neighbourhood_day`); the lifecycle's visit-cap check exempts eating and tray-return statuses (`VISIT_CAP_EXEMPT_STATUSES`) and every visit rating carries a `DEPARTURE_REASONS` reason; and `diagnostics.ts` holds `assertSimulationInvariants`, `simulationDigest` and `stateDigest`. `progression.ts` holds `createDailyObjectives` (fixed templates without a neighbourhood or on day 1, otherwise the internal `create_seeded_objectives`, which picks the kinds from the `objectives` day stream and scales targets from `lastReport` above the fixed floors), the internal `close_finished_day` and `updateProgressionSystems`; `progression.peakReputation` (raised in `settleVisitRating`, never lowered) is what every unlock gate reads, while live `progression.reputation` (the EWMA `next_reputation` in `visits.ts`) drives demand. Command handling is split the same way: `commands.ts` keeps only `dispatchCommand`, which looks the command type up in `COMMAND_HANDLERS` (a mapped type over `GameCommand["type"]`, so a new command without a handler fails to compile, and an unknown type or an inherited key such as `toString` gets the "Unsupported command" rejection through `Object.hasOwn`), plus the settings, stall-upgrade and stall-open handlers; build commands wrap their handler in `with_undo_snapshot`, so the undo snapshot is captured before validation. The internal modules behind it are `build.ts` (one `handle_*` function per build command, each taking `(state, command, before)`), `undo.ts` (`withUndo` and `apply_undo`), `reconcile.ts` (`reconcileWorldTargets` and `reconcileWorldGeometryChange`, which repair guests, queues and seat reservations after a layout change) and `results.ts` (`accept`, `reject` and `commandEvent`). `validation.ts` checks catalog record shapes, then runs `validate_placeables`, `validate_dishes` and `validate_archetypes` in that order through the shared `check_record_identity` and `check_range` rules. Each module keeps its own tuning constants.

4. **`app/game/HawkerSimulator.tsx`** is a `"use client"` component of about 930 lines: the shell that owns the UI state, which modal is open, the focus traps and the callbacks, and composes the HUD, panel and dialog components below. ### Core simulation model

- State is immutable. `dispatchCommand(state, command)` returns `{ state, accepted, error?, events }`. Commands validate everything before they mutate anything. A rejection returns `accepted: false` and leaves the gameplay state as it was.
- `advanceSimulation(state, realDeltaMs)` accumulates real time into fixed steps (`config.fixedStepMs`, 10 Hz). It caps the steps per call by quality mode and drops the excess. `stepSimulation` advances exactly one tick in a fixed order: spawn countdown and spawn (none from last orders in the adaptive model), every customer in `compare_customer_ids` order, the table-cleaning crew (`advance_table_clearing`), then `updateProgressionSystems`. On the first step of a new day, `updateProgressionSystems` closes the finished day first (`close_finished_day`: award the outgoing objectives, then, with a neighbourhood, `roll_neighbourhood_day` builds the report into `lastReport`, a `day-ended` event is emitted and the calendar turns), then regenerates the objectives, then awards objectives and milestones, and finally settles the writer review (`settle_writer_review`).
- Randomness is threaded explicitly: `GameState.rngState` passes through the pure functions in `rng.ts`, which return `{ value, state }`. Never use `Math.random`, wall-clock time, or `localeCompare` in core. The neighbourhood never reads or advances `rngState`: every neighbourhood draw comes from ``hashSeed(`${worldSeed}:${system}:${day}`)`` (`day_stream`), and the tray-return habit from a hash of the guest's ID, so centres without a neighbourhood keep their seeded runs. Use `compareIds` (`ordering.ts`) for any ID ordering that affects results.
- `simulationDigest` / `stateDigest` and `assertSimulationInvariants` exist for determinism and soak tests. Any change to core behaviour should keep the seeded runs reproducible.
- Customers, queues, reservations and uncleared trays exist only at runtime and are not saved. Map, objects, economy, progression (including `peakReputation`), route guides, access points, visit and nutrition metrics, `rngState`, the neighbourhood (`null` when absent), and `elapsedMs` are saved.

### Persistence has three version layers

1. `core/persistence/` is a folder module, imported as `./persistence`. `PERSISTENT_SCHEMA_VERSION` (currently 5) lives in the leaf `core/enums.ts`, so `state.ts` and `types.ts` can use it without an import cycle, and `persistence/index.ts` re-exports it. `index.ts` also holds serialisation and `deserializeGameStateWithReport`, which validates the migrated save against the catalog. `fields.ts` holds the primitive field readers and `PersistenceError` (it must not import `index.ts`), `parsers.ts` the section parsers (the lifetime and today nutrition metrics share the per-intent, per-nutrient and per-dish readers, with prefix-built error paths), `migrations.ts` one `parseVN` per schema version plus the `upgrade_vN_to_vN+1` chain that `migratePersistentState` walks (parse, upgrade, re-parse), and `recovery.ts` the alias and refund recovery of objects and unlocks. In `core/nutrition.ts`, the empty nutrition metrics and their clone share `build_intent_metrics_record`, `build_metric_record` and `clone_day_metrics`, so a new nutrition counter touches one builder and one cloner. The nutrition-metric bookkeeping for a step also lives there: `record_intent_request` (called through `recordIntentRequest` in `arrivals.ts`) and `record_nutrition_sale` (called by `completeSale`, after the request), both pure functions of the metrics and the operating day.
2. The runtime save wrapper (`decodeRuntimeSave` in `runtime/saves.ts`, `runtimeSchemaVersion` 1|2, where `RUNTIME_SCHEMA_VERSION` = 2 is the version written) adds stall menus, dish variants, and `nutritionDataVersion`. If the saved nutrition data version doesn't match the current one, variant choices reset to reviewed defaults.
3. `persistence/saveStore.ts` stores IndexedDB envelopes (`saveVersion`, checksum) in `active` and `backup` slots. At load, the runtime tries each saved candidate in order through `load_runtime_save` and falls back to a new centre.

A change to saved shape needs a version bump at the right layer, a migration, a new frozen fixture in `tests/game/core/persistence/fixtures/`, and a test (see `tests/game/core/persistence/migrations.test.ts`).

### Content and nutrition contracts

- `validateContent` enforces the launch counts in `LAUNCH_ROSTER` (`src/content/roster.ts`): exactly 18 stalls, 91 dishes, 12 archetypes, 2 nutrition source snapshots, 23 nutrition variant families, 5 intents and 11 guidelines, at least 80 placeables, and a nutrition profile total derived as one per dish plus one per non-default variant (171 today), along with localization completeness. The Zod schemas only require these lists to be non-empty. To add or remove content, update `LAUNCH_ROSTER` (and `NUTRITION_GUIDELINE_COUNT` in `tools/nutrition/manifest.mjs` for guidelines; a test keeps the two in step), the localization entries, the "Roster counts" table in `docs/design/CONTENT_CATALOGUE.md`, and the documents that `docs/README.md` lists as restating those counts.
- `src/content/nutrition.generated.json` is generated, so don't hand-edit it. It comes from `tools/nutrition/importer.mjs`, which uses the authored exact mappings in `tools/nutrition/manifest.mjs` and operator-supplied CSVs in the git-ignored `data/` folder (see `docs/design/NUTRITION_DATA.md` for the command). Raw CSVs are never committed, and CSV parsing or fuzzy matching never runs in the browser. The importer delegates CSV parsing and row hashing to `tools/nutrition/csv.mjs` (`parseCsv`, `canonicalRowHash`, `sha256`) the source plausibility rules to `tools/nutrition/plausibility.mjs` (the paired-component floor and fibre ceiling, the drink-family base check and the extreme-outlier fence, each withholding a value as unavailable with the `implausible-source` reason and a finding in the profile's `withheldReasons`), and the rating passes to `tools/nutrition/ratings.mjs` (`MEAL_RATING_WEIGHTS`, `computeRelativeFits`, `nutritionValueForComparison`, `addIntentFits`, `addHealthRatings`), re-exporting the public names (`parseCsv`, `canonicalRowHash` and the five rating names) so callers keep one entry point; `assert_borrowed_parts_allowed` limits Borrowed source rows to `BORROWED_COMPONENT_ALLOWLIST` composite components (never a profile's only or first part); and it names its quarantine thresholds (`COMPONENT_TOLERANCE_G`, `MAX_MACRONUTRIENT_SERVING_RATIO`, the energy cross-check ratios and the manual-review limits). `addHealthRatings` rates each serving on its own against fixed guideline amounts (a meal against a third of HPB and WHO daily references and FSA bands per 100 g edible portion, a dessert in `SNACK_RATED_DISH_IDS` against a snack's share, a drink against Nutri-Grade bands, each condition against stricter clinical references; [ADR 0007](../docs/decisions/0007-guideline-anchored-nutrition-ratings.md), extended by [ADR 0008](../docs/decisions/0008-snack-basis-edible-density-and-source-plausibility.md); a meal's overall rating is half an additive nutrient score and half a condition score (two thirds the mean of the four condition ratings, one third the lowest), less one star per further day past a full day of a limit nutrient, per [ADR 0009](../docs/decisions/0009-whole-profile-overall-health-rating.md), and each meal profile carries those parts in `healthParts`, with the daily amounts in the content's `dailyReference`), so a rating never depends on the rest of the menu, while `addIntentFits` still ranks intents relatively within a class. The manifest's `NUTRITION_REVIEW_REVISION` is part of `dataVersion`; raise it whenever the mappings or the rating model change, so saved recipe-variant choices reset to the reviewed defaults. A composite profile sums exact source rows listed in its `components`, and a profile's `ratingInputs` (edible amount and rule stand-ins) feed only the ratings. All five files are `// @ts-check` with JSDoc types from `src/content/types` and are listed in the `tsconfig.json` include, so `npm run typecheck` checks them; `checkJs` stays off globally.
- Dishes have two independent ratings: the Star rating (taste and popularity, authored) and the Health and condition ratings (per-serving fit against guideline amounts, generated). Health conditions must stay independent of customer personas and demographics. UI copy must not label dishes good or bad or make medical claims.

### Hosting and security

- Response headers live only in `src/config/securityHeaders.ts`, which both `next.config.ts` and `worker/index.ts` consume. The CSP is `connect-src 'self'`.
- Build mode and the developer `?debug` / `?visualQa` query flags are read only through `src/config/env.ts` (`IS_PRODUCTION_BUILD`, `IS_DEVELOPMENT_BUILD`, `has_dev_query_flag`). Call sites test `!IS_PRODUCTION_BUILD` before `has_dev_query_flag` so Vite drops the developer-only branches from production bundles. `vite.config.ts` and `tools/*.mjs` run in Node and are the documented exceptions.
- By design there is no backend, account, analytics, telemetry, or payment, and gameplay doesn't depend on the network (ADR 0003). The service worker and its save-gated update flow live in `public/sw.js` and `src/game/pwa/registerPwa.ts`, which owns the page-to-worker protocol (`SW_MESSAGE`, `WARM_CACHE_TIMEOUT_MS`) and `activate_waiting_update`; the component saves first and calls it only when the save succeeds.

## Docs conventions

- `docs/decisions/README.md` (the decision log) requires a new ADR in `docs/decisions/` for any reversal that affects persistence, content IDs, rendering perspective, offline behaviour, the accessibility boundary, or release compatibility. Balance tweaks go in `docs/CHANGELOG.md` instead.
- The docs deliberately avoid calling the build production-approved, and edits must keep it that way. Package and cache version numbers do not indicate release state.
